## BLOCKING issues

1. D-PACE reduction does not match the frozen minibatch description.

   - The proposal defines \(\mathcal L=(1/N)\sum_{n=1}^N\cdots\) with \(N=4\).
   - The plan/contract define one prompt with four anchors.
   - The pinned implementation divides the summed anchor/position loss by tensor batch size `bsz`, not anchor count: [dflash.py](/hpc2hdd/home/zwang668/dflash-iclr/third_party/D-PACE/specforge/core/dflash.py:376). A tensor layout of `bsz=1`, four anchors therefore produces four times the frozen proposal loss.
   - This changes the D-PACE/frontier relative scale and invalidates claimed scalar/gradient parity.

   Exact fix: freeze each outer minibatch as four tensor-batch rows, each holding one forced complete anchor from the same source prompt: `source_prompts=1`, `tensor_batch_size=4`, `anchors_per_row=1`, `reduction_divisor=4`. Thus 8,000 prompts × four blocks / batch four remains exactly 8,000 outer steps. Add these fields to JSON and parity-test the full scalar and flattened gradient against the pinned implementation. Do not use `bsz=1, anchors=4` unless the proposal loss and frontier coefficient are formally changed and re-reviewed.

2. Verifier ground truth and anchor construction are not frozen exactly.

   The documents say “target-greedy continuation” but never explicitly define \(y_i\) as verifier-generated truth rather than a draft/comparator prediction. They also do not freeze the offset formula.

   Exact fix: specify that the frozen target alone autoregressively generates the greedy continuation using float32 decision logits and lowest-ID tie-breaking. For offset \(o_n\), the anchor is `continuation[o_n]` and \(y_{n,i}=\text{continuation}[o_n+i]\), \(i=1,\ldots,15\); target context/features contain tokens strictly before the anchor. No released/adapted DFlash, Domino, or other comparator may define or filter a gold label. This makes prefix matching exactly verifier acceptance along the matching prefix.

   Freeze the existing local offset formula:

   ```text
   maximum = continuation_length - 16
   offsets[j] = int(round(j * maximum / 3)), j=0,1,2,3
   ```

   with Python rounding and an assertion of four distinct complete offsets.

3. The 16-token minimum is incompatible with four complete distinct b16 anchors.

   The local collector yields only one complete anchor for a 16-token continuation. Four distinct anchors require at least 19 continuation tokens under the canonical formula. This conflicts across [EXPERIMENT_PLAN.md](/hpc2hdd/home/zwang668/dflash-iclr/refine-logs/prospective-v2/EXPERIMENT_PLAN.md:74), [PROSPECTIVE_V2_CONTRACT.md](/hpc2hdd/home/zwang668/dflash-iclr/refine-logs/prospective-v2/PROSPECTIVE_V2_CONTRACT.md:127), and JSON `minimum_continuation_tokens=16`.

   Exact fix: change the minimum to 19 everywhere and require exactly four blocks per retained prompt. Short prompts consume the next pre-frozen same-domain, same-split reserve entry automatically; attempted entries are permanently consumed and never reassigned.

4. Native LoRA execution and merge dtype are underspecified and internally inconsistent.

   Verified native paths are:

   ```text
   layers.{3,4}.self_attn.{q,k,v,o}_proj
   layers.{3,4}.mlp.{gate,up,down}_proj
   ```

   The count is correct:

   | Module | Parameters/layer |
   |---|---:|
   | q | 106,496 |
   | k | 57,344 |
   | v | 57,344 |
   | o | 106,496 |
   | gate/up/down | 196,608 each |
   | Total/layer | 917,504 |
   | Two layers | 1,835,008 |

   However, LoRA parameter/compute dtype and A initialization are not frozen. More seriously, the contract says merged weights remain float32 while the released graph is bf16 and trace dtype must be identical. A float32 linear weight receiving bf16 activations is not a valid un-autocast released path.

   Exact fix:

   - Freeze A/B master parameters and Adam moments as float32.
   - Freeze A initialization, recommended `kaiming_uniform_(a=sqrt(5))`, with sorted module-path enumeration and a per-training-seed generator; B is exactly zero.
   - Compute the LoRA branch in float32, cast its delta to the base-output dtype before addition.
   - Define “float32 merge” as float32 accumulation only:
     `merged = (base.float() + scale * B @ A).to(base.dtype)`.
   - Store/runtime weights remain bf16, wrappers are removed, and the ordered runtime graph/dtypes match released DFlash.
   - Record per-module A/B hashes. Matched arms under a seed must begin from identical A/B values.

   Partial `torch.func.functional_call(..., strict=False)` over LoRA parameters is supported by the pinned PyTorch and is feasible.

5. Successful-restoration transaction semantics are incomplete.

   The frozen text does not say whether a successfully restored infeasible minibatch then attempts its task update, whether gradients/masks are recomputed, or whether successful restoration survives a subsequent task skip.

   Exact fix: freeze this transaction:

   1. Restore from batch-start parameters with no moment or `t_adam` mutation.
   2. Once feasible, recompute logits, all detached indices/masks, task gradient, constraints, and VJP at the restored parameters.
   3. Attempt the ordinary projected task transaction on the same minibatch.
   4. If that task skips, retain the successfully restored parameters but keep moments and `t_adam` unchanged.
   5. Failed restoration restores batch-start parameters and aborts the run.
   6. Increment `k_outer` exactly once after the minibatch.
   7. Stable-tie projection order is block row 0–3.

   Tests must cover successful-restoration-plus-commit, successful-restoration-plus-skip, and failed-restoration rollback.

6. Statistical references and CI construction are not executable.

   `first-token lower ≥ -.005` is undefined unless it is a contrast; as an absolute indicator it is almost vacuous. `D–C harm` could mean either a difference of released-referenced harm rates or direct \(D<C\) harm. Mean-harm precision lacks sidedness. The bootstrap quantile construction and power algorithm are also unspecified.

   Exact fix:

   - Define \(H^M=1[a^M<a^{Released}]\).
   - Define mean harm as \((a^{Released}-a^M)_+\).
   - Define first-token contrast as
     \(1[a^M\ge1]-1[a^{Released}\ge1]\).
   - Define C2 harm as \(H^D-H^C\), not \(1[a^D<a^C]\).
   - Checkpoint first-token gates are per-arm/per-seed versus released.
   - Freeze percentile cluster-bootstrap quantiles and interpolation: two-sided 95% uses `.025/.975`; one-sided 95% uses `.05` or `.95`.
   - State whether mean-harm precision is one-sided upper-bound distance ≤.03 or two-sided half-width; recommended is one-sided to match its claim gate.
   - Define `n_power` as the maximum required by every registered superiority, non-inferiority, and precision requirement, using one frozen ICC/cluster adjustment or simulation algorithm. Add all effect sizes and precision constraints to JSON.

7. Component-atomic split and reserve semantics are not fully feasible as written.

   Exact domain quotas may conflict with whole connected components; cross-domain components make “domain-stratified component bootstrap” undefined. Reserve replacement could also move part of a component across splits.

   Exact fix:

   - Freeze normalization, 8-gram tokenization, Jaccard candidate generation, union-find ordering, and component ID hashing.
   - Either exclude cross-domain components before allocation or define a frozen component-level mixed-domain stratum. Exclusion is simpler and preserves the three registered strata.
   - Assign every active and reserve candidate’s complete component to exactly one split before sequence generation.
   - Freeze deterministic component/row ordering and an exact quota allocator.
   - Unused rows from a component may only remain discarded or reserve entries for that same split.
   - If exact quotas or sufficient reserves cannot be achieved, the data gate fails; no component splitting or manual replacement is allowed.
   - Falsifier reserve attempts count as the same single opening, remain sealed in logs, and cannot later enter another split.

8. The A/D cost benchmark can accidentally measure \(K=0\).

   “Complete \(K\le4\)” does not require any protected row. If all frozen first mismatches are at position 1, D bypasses the batched VJP and projection, invalidating the overhead gate.

   Exact fix: every warmup and timed D minibatch must assert all four protected sets are nonempty, hence `K=4`. Emit `K` and protected-position-count histograms in each receipt. A must still execute only real D-PACE work; D must include its frozen-reference forward, four-row VJP, projection/restoration when triggered, and every exact candidate forward.

9. Checkpoint identities and one-opening behavior conflict.

   The proposal says “five model identities”; the plan says five system definitions but 13 concrete instances; the contract says 12 selected checkpoints even though an infeasible arm/seed only has diagnostic `T_final`.

   Exact fix: distinguish five system definitions from 13 concrete model instances. Before opening, freeze released plus 12 per-arm/per-seed hashes, each labeled `selected_feasible` or `diagnostic_T_final`. Define whether C1 may proceed when a control seed is diagnostic and which C2 claims automatically fail. Never call a diagnostic fallback “selected.”

10. Authorization ladders conflict and C1/latency is circular.

   The plan has G0–G8 and separately opens capacity then training. The Markdown contract has G0–G7 and requires a capacity pass before capacity was explicitly opened. The plan says C1 includes latency, while latency opens only after C1 passes.

   Exact fix: use one ladder everywhere:

   | Gate | Opens |

   | G0 | local implementation and CPU/mock tests only |
   | G1 | one synthetic GPU smoke |
   | G2 | exactly three A/D cost pairs |
   | G3 | power and split materialization/audit |
   | G4 | fit/checkpoint sequence generation |
   | G5 | 32/512-block capacity only |
   | G6 | 4×3 main training |
   | G7 | one common falsifier opening |
   | G8 | latency after all non-latency C1 gates and merge/trace pass |

   Final C1/deployment-equivalence adjudication occurs after latency. Regenerate JSON with this ladder.
